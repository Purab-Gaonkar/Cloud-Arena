1. Project overview

CloudArena is a 1v1 arcade fighting game in the spirit of Street Fighter and Tekken. Two fighters battle across best-of-N rounds on atmospheric, layered stages, using combos, heavy attacks, blocks, throws, dashes and a cinematic super move. The game will be playable offline against the computer or a friend on the same PC, and online against players anywhere through a cloud-hosted, server-authoritative backend.

Vision: a polished, replayable fighting game that works fully offline and scales to online play on cloud infrastructure that is cheap when idle and elastic under load.

3. Scope

3.1 In scope

  • Desktop game client built with Godot 4 (Windows; Linux build for the dedicated server).
  • Game modes: VS CPU, Local 2-Player, Training, Online Match.
  • Three fighters, four stages, configurable round rules.
  • Gamepad support and fully rebindable controls.
  • Music, sound effects and volume settings from licence-compatible assets.
  • Cloud backend: WebSocket game server, matchmaking and statistics API, Redis, NGINX, Terraform deployment.
  • Automated testing, build/export pipeline and release packaging.

3.2 Out of scope

  • Mobile and console ports.
  • Player accounts, payments, cosmetic store, ranked ladders.
  • Replays, spectator mode and tournament tools.
  • Rollback netcode (the first online release is server-authoritative).

Architecture

 Godot 4 clients ──HTTP / WebSocket──▶  NGINX load balancer
                                          • ip_hash   → game servers (sticky WebSocket)
                                          • least_conn → matchmaking API
                                   ┌───────────────┴───────────────┐
                        Game servers 1..N (:8765)       Matchmaking API 1..N (:8000)
                        websockets, 60 Hz tick          FastAPI
                                   └───────────────┬───────────────┘
                                            Redis 7 (:6379)
                          matchmaking queue · room metadata · win leaderboard

Design principles: the server owns the simulation and clients send inputs only; services are stateless and scale by adding instances; all shared state lives in Redis; infrastructure is fully described as code.

8. Assumptions, constraints and dependencies

  • Assumptions: players use Windows 10/11 with a Direct3D 12 or Vulkan GPU; online play targets a single GCP region at first; two developers are available throughout.
  • Constraints: Cloud Run closes idle WebSockets after 5 minutes; connections must reach the same instance as their room; extra move art is generated from existing sprites rather than hand-drawn; fixed team size.
  • Dependencies: Godot 4, a GCP project with billing, Docker, Terraform, and the free/CC0 art and audio packs listed in section 10.

9. Risks and mitigations

#RiskImpactMitigation
1Latency makes online combat feel sluggishHighServer-authoritative first, forgiving timing windows, region choice; evaluate prediction or rollback later.
2Client and server drift apart on combat rulesHighSingle shared message contract, resolve all hits server-side, integration tests every week.
3WebSocket idle timeouts or affinity failures on Cloud RunMedium20 s keepalive, sticky routing, health checks and room expiry.
4Cloud cost grows with playersMediumScale-to-zero, small Redis tier, budget alerts, Terraform teardown.
5Balance issues or exploitsMediumData-driven stats, combo scaling, wake-up invulnerability, training mode and automated soak tests.
6Asset licence problemsMediumUse CC0 or clearly licensed packs only; maintain credits.
7Generated sprites look weaker than hand-drawn artMediumStable file names so replacement art drops in without code changes.
8Schedule slips with a small teamMediumParallel client and backend tracks, MUST features first, COULD features cut first.

11. Acceptance criteria

  1. From a cold start the game reaches the main menu and a VS CPU match begins within 60 seconds with no errors.
  2. Every combat action works for both players on keyboard and gamepad; all bindings can be changed and persist.
  3. A super can be dodged; its cinematic appears only when the first hit connects; a hit during start-up cancels it.
  4. Two players on different machines find each other through matchmaking and finish a full online match with the same rules as local play.
  5. Match results appear on the global leaderboard.
  6. The backend deploys from scratch with Terraform and scales out under a load test without dropped matches.
  7. Automated test suites (gameplay soak, API, WebSocket load) pass on every release build.
